# 의사결정기록 001: 왜 MySQL이 아닌 PostgreSQL을 선택하는가

## 상태
대체됨 (Superseded by 002)

## 일자
2026-05-08

## 배경
이 프로젝트는 멀티브로커 포트폴리오 대시보드 MVP이며 다음 특성이 있다.
- 실시간 시세 반영
- 임계치 기반 알림 + 중복방지/재무장전 로직
- 지연 KPI 추적 (`quote p95 <= 1s`, `alert dispatch p95 <= 2s`)
- KIS 단일 브로커에서 멀티브로커 확장 예정

### 용어 설명: 알림지연 p95
- 알림지연: "알림 조건이 충족된 시점"부터 "알림 발송을 시작한 시점"까지 걸린 시간
- p95(95 퍼센타일): 전체 알림 100건 중 느린 5건을 제외한 95건이 이 시간 이내에 처리된다는 뜻
- `alert dispatch p95 <= 2s` 의미: 대부분의 알림(95%)은 2초 안에 발송 시작되어야 함

주요 영속 데이터 저장소로 MySQL/MariaDB와 PostgreSQL을 비교했다.
- 사용자/계정 메타데이터
- 브로커 연결 정보
- 알림 규칙/이력
- 포트폴리오 스냅샷(집계/리포팅)

### 항목별 코멘트 (왜 PostgreSQL이 유리한가)
1. 사용자/계정 메타데이터
- 기본 CRUD 중심이라 MySQL도 충분히 가능하다.
- 다만 권한/감사/활동 이력 조회가 늘어날 때 조인/집계 확장성을 고려하면 PostgreSQL이 장기적으로 유리하다.

2. 브로커 연결 정보
- 브로커별 인증정보 구조가 달라질 수 있어 일부 유연한 필드 관리가 필요하다.
- PostgreSQL은 관계형 무결성을 유지하면서도 JSONB 기반 확장을 함께 가져가기 좋다.

3. 알림 규칙/이력
- 중복방지/재무장전 로직은 상태 전이와 트랜잭션 정합성이 핵심이다.
- PostgreSQL은 이러한 상태성 데이터 처리와 이후 지연/성공률 집계 쿼리를 함께 다루기 편하다.

4. 포트폴리오 스냅샷(집계/리포팅)
- 이 항목은 분석/통계 쿼리 비중이 높아질 가능성이 가장 크다.
- PostgreSQL은 백분위(p95), 시계열 집계, 복합 조건 리포팅을 비교적 단순한 SQL로 구현하기 유리하다.

## 결정
주요 관계형 데이터베이스는 PostgreSQL을 사용한다.

## PostgreSQL 선택 이유 (프로젝트 기준)
1. 예상되는 분석/집계 쿼리에 더 잘 맞는다.
- 브로커/시장별 수익률 집계, 지연 통계(p95) 등 분석성 쿼리가 필수다.
- PostgreSQL은 고급 집계/백분위 계산을 더 단순한 SQL로 표현하기 쉽다.

2. 확장 시나리오에 유리하다.
- 멀티브로커 확장 시 브로커별 메타데이터와 리포팅 차원이 늘어난다.
- PostgreSQL은 관계형 무결성을 유지하면서도(JSONB + 인덱싱 등) 확장 옵션이 좋다.

3. 알림 상태머신의 정합성 유지에 적합하다.
- 중복방지/재무장전 로직은 트랜잭션 일관성과 잠금 동작이 중요하다.
- PostgreSQL은 표준 트랜잭션 패턴으로 이를 안정적으로 처리할 수 있다.

4. 장기 유지보수 복잡도를 낮춘다.
- 단순 CRUD만 보면 MySQL도 충분하다.
- 하지만 본 프로젝트는 통계/분석 요구가 커질 가능성이 높아 PostgreSQL 쪽이 장기적으로 유리하다.

## 이 결정이 의미하지 않는 것
- MySQL이 기술적으로 불가능하다는 뜻은 아니다.
- Day-1 개발 편의가 아니라, 다음 단계 복잡도까지 고려한 선택이다.

## 영향
### 장점
- 지표/분석 쿼리 구현이 간결해진다.
- 멀티브로커 확장 시 데이터 모델 진화가 수월하다.
- 우회성 SQL/애플리케이션 보정 로직을 줄일 수 있다.

### 단점
- PostgreSQL 경험이 적은 팀원은 러닝커브가 있다.
- 초기 운영 기준(백업/권한/모니터링) 문서화를 더 엄격히 해야 한다.

## 실행 메모
1. 영속 도메인 데이터는 PostgreSQL에 저장한다.
2. Redis는 캐시/실시간 임시상태/중복방지 보조 상태로 사용한다.
3. 스키마는 마이그레이션 기반으로만 관리한다(수동 드리프트 금지).
4. KPI 관련 엔드포인트는 SQL 리뷰 체크를 둔다.

## 재검토 조건
아래 조건 중 하나가 발생하면 이 결정을 재검토한다.
- 팀 운영 제약상 MySQL 생태계가 압도적으로 유리한 경우
- 제품 범위가 장기적으로 단순 CRUD에 머물고 분석/통계 요구가 사실상 사라지는 경우
