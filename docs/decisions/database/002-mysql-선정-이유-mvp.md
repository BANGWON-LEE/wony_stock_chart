# 의사결정기록 002: MVP는 MySQL로 구현한다

## 상태
확정 (Accepted)

## 일자
2026-05-08

## 배경
- 팀은 MySQL 사용 경험이 있고, PostgreSQL 실무 경험은 없다.
- 현재 목표는 멀티브로커 포트폴리오 대시보드 MVP를 빠르게 구현/검증하는 것이다.
- KPI는 유지한다: `quote p95 <= 1s`, `alert dispatch p95 <= 2s`

## 결정
MVP의 주요 관계형 데이터베이스는 MySQL을 사용한다.

## 선택 이유
1. 개발자 친숙도/숙련도를 우선한다.
- 익숙한 DB를 쓰면 초기 설계/구현/운영 속도가 빨라진다.
- 장애 대응과 성능 튜닝도 팀이 바로 대응할 수 있다.

2. 현재 MVP 범위는 MySQL로 충분히 커버된다.
- 사용자/계정 메타데이터, 브로커 연결 정보, 알림 규칙/이력, 포트폴리오 스냅샷 저장은 MySQL로 안정적으로 구현 가능하다.
- 트랜잭션, 인덱스, 조인, 윈도우 함수(MySQL 8+)로 필요한 기능을 충족할 수 있다.

3. PostgreSQL의 장점은 인정하되, 지금은 실행 속도가 더 중요하다.
- PostgreSQL은 고급 분석 SQL 표현이 간결한 장점이 있다.
- 그러나 현재 단계에서는 팀 숙련도 기반의 구현 속도와 운영 안정성이 더 큰 가치다.

## 항목별 코멘트 (MySQL로도 충분한 근거)
1. 사용자/계정 메타데이터
- 전형적인 CRUD/인증 데이터이며 MySQL이 강한 영역이다.

2. 브로커 연결 정보
- 관계형 구조 + 암호화된 자격증명 저장 패턴은 MySQL에서 일반적으로 잘 운영된다.
- 브로커별 확장 필드는 스키마 확장/별도 테이블 분리로 대응 가능하다.

3. 알림 규칙/이력
- 상태 전이(armed/triggered/rearm)와 중복방지는 트랜잭션 + 조건부 업데이트로 구현 가능하다.
- p95 계산은 초기에는 배치/애플리케이션 집계로도 충분히 운영할 수 있다.

4. 포트폴리오 스냅샷(집계/리포팅)
- 기본 집계/시계열 조회는 MySQL 인덱스 설계로 대응 가능하다.
- 고급 통계가 복잡해지면 집계 테이블/배치 파이프라인으로 확장한다.

## 영향
### 장점
- 구현 착수 속도가 빠르다.
- 팀 커뮤니케이션/디버깅/운영 효율이 높다.
- 초기 리스크를 줄이고 MVP 학습 사이클을 단축한다.

### 단점
- 고급 통계 쿼리에서 SQL 복잡도가 높아질 수 있다.
- 장기적으로 분석 요구가 커지면 추가 최적화가 필요할 수 있다.

## 실행 메모
1. MySQL 8+ 기준으로 개발한다.
2. 스키마는 마이그레이션으로만 관리한다.
3. p95/리포팅 쿼리는 초기엔 앱/배치 집계로 구현하고, 필요 시 SQL 고도화한다.
4. DB 종속 기능은 최소화해 전환 가능성을 열어둔다.

## 재검토 조건
- 알림/리포팅 통계 쿼리 복잡도가 크게 올라 유지보수 비용이 증가하는 경우
- KPI 달성 실패가 DB 쿼리 한계에서 반복적으로 발생하는 경우
- 팀의 PostgreSQL 숙련도가 확보되어 전환 이점이 명확해지는 경우
