# MVP 시스템 기술설계서 v0

## 1. 문서 목적
- 멀티브로커 포트폴리오 대시보드 MVP를 구현 가능한 수준으로 구체화한다.
- PRD의 기능 요구사항을 API, 데이터모델, 처리흐름, 운영기준으로 변환한다.

## 2. 범위
### 포함
- 인증(회원가입/로그인)
- 브로커 연결 등록(MVP: KIS)
- 포트폴리오 요약/보유종목 조회
- 실시간 시세 구독(WebSocket)
- 임계치 알림 규칙 CRUD 및 이력 조회
- 알림 중복방지/재무장전 로직

### 제외
- 주문/자동매매
- 리밸런싱 추천
- 멀티브로커 실연동(구조만 준비)

## 3. 기술 스택(확정)
- Frontend: React 19 + TypeScript + Vite + Tailwind CSS (Web/PWA)
- Backend: Node.js 기반 API + WebSocket 서버
- DB: MySQL 8+ (의사결정기록 002 반영)
- Cache/State: Redis

## 4. 시스템 구성
- `frontend`: 사용자 화면(포트폴리오, 차트, 알림설정)
- `api-server`: 인증, 포트폴리오, 알림 규칙 REST API
- `quote-gateway`: 브로커 시세 구독 및 내부 표준 포맷 변환
- `alert-engine`: 임계치 판정, dedup/re-arm, 알림 발송
- `mysql`: 영속 데이터 저장
- `redis`: 실시간 상태/구독 세션/중복방지 보조 상태

## 5. 핵심 데이터 모델
### User
- `id`, `email`, `password_hash`, `created_at`

### BrokerConnection
- `id`, `user_id`, `broker_type`, `encrypted_credentials`, `status`, `created_at`, `updated_at`

### Position
- `id`, `user_id`, `broker_type`, `symbol`, `market`, `quantity`, `avg_price`, `current_price`, `currency`, `updated_at`

### PortfolioSnapshot
- `id`, `user_id`, `total_value`, `total_pnl`, `total_return`, `base_currency`, `snapshot_at`

### AlertRule
- `id`, `user_id`, `scope`(`portfolio`|`symbol`), `symbol`, `direction`(`above`|`below`), `target_value`, `state`(`armed`|`triggered`), `enabled`, `created_at`, `updated_at`

### AlertEvent
- `id`, `rule_id`, `trigger_value`, `triggered_at`, `dispatch_started_at`, `channel`, `delivery_status`

## 6. API 명세(초안)
### Auth
- `POST /auth/signup`
- `POST /auth/login`
- `POST /auth/refresh`
- `POST /auth/logout`

### Broker
- `POST /brokers/connections`

### Portfolio
- `GET /portfolio/summary`
- `GET /portfolio/positions`

### Alerts
- `POST /alerts/rules`
- `GET /alerts/rules`
- `PATCH /alerts/rules/:id`
- `DELETE /alerts/rules/:id`
- `GET /alerts/history`

### WebSocket Events
- Client -> Server: `subscribe_quotes`, `unsubscribe_quotes`
- Server -> Client: `quote_update`, `portfolio_tick`

## 7. 처리 흐름
### 실시간 시세
1. 클라이언트가 `subscribe_quotes` 전송
2. 서버가 KISAdapter 구독 시작
3. 이벤트를 내부 표준 스키마로 변환
4. Redis/메모리 상태 갱신 후 구독 세션에 fan-out
5. 클라이언트 차트 업데이트

### 알림 판정
1. 시세/평가 업데이트 수신
2. 사용자 활성 규칙 조회
3. crossing 판정
4. `armed -> triggered` 상태 전이(조건부 업데이트)
5. 알림 발송 시작 및 `AlertEvent` 기록
6. 반대 방향 crossing 시 `triggered -> armed` 복귀

## 8. 정합성/중복방지 규칙
- 동일 규칙은 동일 방향 crossing에서 1회만 발송
- 중복 방지 키: `rule_id + state + direction`
- 상태 전이는 트랜잭션으로 처리한다.
- 병렬 처리 충돌 방지를 위해 조건부 업데이트를 사용한다.

## 9. 성능 목표 및 측정
- `quote reflection p95 <= 1s`
- `alert dispatch start p95 <= 2s`

### 측정 정의
- quote reflection: 백엔드 시세 이벤트 수신 시점 ~ 클라이언트 반영 시점
- alert dispatch start: 규칙 충족 시점 ~ 알림 채널 발송 시작 시점

## 10. 보안 기준
- 브로커 자격증명 평문 저장 금지(암호화 저장)
- 로그/에러 응답에서 토큰, 계좌번호 마스킹
- 리소스 접근 시 사용자 소유권 검증 필수
